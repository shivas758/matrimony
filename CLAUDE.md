# Matrimony Agents App — Project Instructions

You (Claude) are building **Wedbook** (called *Mediator* until v2.7), a matrimony profile-sharing platform for marriage bureau agents.
Read `docs/SPEC.md` fully before writing any code. It is the source of truth.

## Stack (fixed — do not change)
- **Mobile apps:** Flutter (Android-first). The agents' app **Wedbook Agent** (*Mediator* until v2.7; "Mediator" stays its internal code name) lives in `app/` (package `com.matrimonyagents.matrimony_agents`); the customers' app **Wedbook Matrimony** (*MILI* in v2.7, *Gandharva* before; "Gandharva" stays its internal code name) lives in `customer_app/` (package `com.matrimonyagents.gandharva`). Both package ids are kept so installs update in place. Both talk to the same backend.
- **Backend:** Node.js 20 + Express + PostgreSQL 16. Lives in `backend/`. Runs via Docker Compose.
- **Database schema:** `backend/db/schema.sql` (already written, with seed data). Extend it there; use numbered migration files `backend/db/migrations/00X_*.sql` for later changes.
- **Auth:** JWT (access token, 30-day expiry is fine for v1). Passwords hashed with bcrypt.
- **Photos:** stored on server disk under `backend/uploads/`, served via authenticated routes; public share pages get watermarked copies only.
- **Deployment target:** Oracle Cloud Always Free ARM VM (Ubuntu 24.04, arm64). All Docker images must support linux/arm64. Deployment steps in `deploy/ORACLE_SETUP.md`.

## Core business rules (never violate)
1. Agents only see profiles that are *shown to* one of the agent's selected communities. Agents get 3 communities free (at most 3 at signup); each further one costs ₹1000 once, paid by UPI and verified by an admin (SPEC §9.20 C); admins set communities freely. A profile is always shown to its own community; its family may additionally choose more communities, or all of them (the community audience, SPEC §9.18 E) — nobody else can widen it. An agent who is not yet *approved* (fewer than 10 live clients, SPEC §9.23 A) sees only their own uploads and clients. Admins see all real profiles. Store-review demo accounts (SPEC §9.21) live in a separate demo world: they see only demo profiles, and nobody else (admins included) sees demo profiles. A profile the viewer blocked is hidden from them, and between families a block works both ways (SPEC §9.22).
2. New agents are `active` right after signup (no admin activation since v2.13) but *not approved*: they see only their own uploads and clients and are not in the customers' agents list until they have 10 live clients (customers with a published profile), when approval is stamped automatically (an admin may also approve by hand); once approved, always approved (SPEC §9.23 A). Every agent gets 10 free gift codes once (admins can add more); a customer who enters one at publish is linked to that agent and the profile goes live free and without a separate approval (SPEC §9.23 B). Forgotten passwords (agents and customers) are reset by the user with an OTP to their phone — *Forgot password?* (SPEC §9.24 D); an admin can still give an agent a temporary password (→ forced change on next login); the app never emails anything. Signups and password resets (agents and customers) verify the phone with an OTP — mock provider by default (`OTP_PROVIDER=mock`, code `123456`); real codes by env — StartMessaging (`OTP_PROVIDER=startmessaging`, the owner's choice), Fast2SMS, MSG91, or Firebase phone auth (`OTP_PROVIDER=firebase`: the app does the SMS, the server verifies the Firebase ID token) (SPEC §9.19). Customers (Wedbook Matrimony) log in with phone + password like agents since v2.14 (SPEC §9.24 C; customers from before then got `123456`); the OTP is used only at signup and for a reset. A new customer starts as a `guest` (no agent; browses only photo + age, job, caste, package cards) and may fill in their whole profile before choosing an agent; the agent link and the fee come at **Publish** (SPEC §9.23 C). They become `pending` when they link an agent, and `active` when that agent approves (or at once with that agent's gift code). Opening profiles and interests needs an active account AND at least one profile paid for (₹150 registration fee per profile, `PAYMENT_PROVIDER=mock` by default; in production `PAYMENT_PROVIDER=upi`: paid by UPI to the owner's UPI ID and verified by an admin, SPEC §9.20 — gateways refuse matrimony; Play Store builds (`--dart-define=STORE=play`) show no non-Google payment). A customer profile is visible to others only when it is paid (in the app, or recorded as cash by the agent) AND its customer is active (SPEC §9.12–9.13). A paid profile is deleted only with the agent's (or an admin's) approval.
3. Any active agent can share/download any visible profile — but shared content and downloads must NEVER include the "on request" fields (SPEC §9.8: contact phone numbers, parents' names/occupations/phones, contact person, native place `city`/`state`, birth place, exact work place / NRI place, siblings, family details, property) or uploader identity — nor any detail the family switched off with the privacy toggles, nor the profile ID (rule 8). Work country / NRI country are the public location.
4. The same "on request" fields are hidden in-app too. For agents, access requires a contact request approved by the profile's uploader or an admin; for customers, access to another profile requires their *interest* to be accepted by that profile's uploader or an admin. Approval expires 15 days after approval. Admin (or the approver) can revoke early. **Privacy toggles (SPEC §9.18 D):** a family can switch off any other detail of their profile (name, date of birth, community, education, income, horoscope, extra photos, …); a switched-off detail is treated exactly like an on-request field everywhere — lists, filters, search, shares, the PDF, `/p/:token`, photo routes, request rows, notifications. Only the main photo, age and gender are always shown. A hidden name is replaced by the neutral label `Profile <id>`.
5. Every share and every contact approval is logged (share_logs, contact_requests).
6. Public share links (`/p/:token`) show a masked profile page: photos (watermarked), bio, community, education, horoscope — no contacts, no uploader info. Links can be deactivated.
7. A customer belongs to at most one agent (exactly one once linked) and owns at most one profile (SPEC §9.17); every profile's `uploaded_by` is always that agent (a customer's profile has no uploader until they link one, SPEC §9.23 C). Since v2.14 agents do not add profiles at all — every profile comes from a family (the Wedbook Matrimony app or the agent's registration form); `POST /api/profiles` is off unless `AGENT_PROFILE_UPLOADS=true` (tests only) (SPEC §9.24 A). Changing agent needs the current agent's (or an admin's) approval and moves the profile with the customer (a guest / pending / rejected customer may simply link another agent). Customers never see who uploaded a profile; the two agents involved in an interest see each other's name, agency, phone and agent code so they can talk.
8. **Agent codes and profile IDs (SPEC §9.18 B / C).** Every agent has a permanent code — state code + number + letter(s), numbered per state: `KA1A, KA1B … KA1Z, KA2A … KA999Z, KA1AA …` — issued when they choose their State (at signup; agents from before v2.8 once, in the app). Every profile has a permanent ID `GN-<agent code>-<letter><3 digits>` (`GN-KA1A-A001`), numbered per agent. Neither ever changes (a profile keeps its ID when its customer changes agent) and no code is ever reused — the counters only count up. The profile ID carries the agent's code, so it is uploader identity: only the profile's own agent, admins and the owning customer may see or search it — never other agents, other customers, shares, PDFs or public pages.

## Working style
- Build backend first, test with curl, then build the Flutter app against it.
- Keep the API base URL in one Flutter config file (`app/lib/config.dart`) so it can point to localhost during dev and the Oracle VM in production.
- Write seed/master data only via schema.sql or migrations — never hardcode master lists in app code; the app must fetch them from the API.
- When the user asks for a new feature, update `docs/SPEC.md` first, then implement.
- Target: a working APK the user can send to agents over WhatsApp (no Play Store needed for v1).

## Directory map
- `docs/SPEC.md` — full specification (schema, screens, API, permissions)
- `backend/` — Express API + Docker Compose + SQL
- `app/` — Flutter app for agents (Wedbook Agent; code name Mediator)
- `customer_app/` — Flutter app for customers (Wedbook Matrimony; formerly MILI / Gandharva)
- `deploy/ORACLE_SETUP.md` — copy-paste server setup for the Oracle VM
